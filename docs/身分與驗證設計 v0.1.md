# 身分與驗證設計 v0.1

日期：2026-11-12　狀態：草稿，待 Dino 確認方向後再實作。不含程式碼。

## 一、目標

1. 多個服務（adventure、trilog、之後的新服務）使用**同一種驗證方式**：帳號密碼加 Google 登入，符合主流服務形式。
2. 服務可以放在不同位置（Cloudflare、Vercel、其他），不因主機不同而換驗證方式。
3. 登入要方便：手機（含 iOS 主畫面網頁）登入一次，很久不用再登。
4. trilog 可能對外開放註冊，所以**驗證與身分必須和各服務分開**，且預設拒絕：沒有被授權的人，即使有帳號也進不去私人服務。

## 二、原則

1. **認證（你是誰）與授權（你能做什麼）分開。** 認證集中在身分服務；授權由各服務自己決定。
2. **只用標準 token（JWT，OIDC 風格）。** 各服務用身分服務公開的金鑰（JWKS）自己驗證簽章，不呼叫身分服務、不共用資料庫，因此與服務放哪裡無關。
3. **預設拒絕。** 服務只放行名單或角色上有的人；開放註冊只代表「能有帳號」，不代表「能進任何服務」。
4. **不自己發明登入。** 密碼、驗證信、重設密碼、OAuth 流程都交給身分服務，各服務只處理 token。
5. **機密不進程式碼、日誌與文件。**

## 三、架構

```
        ┌──────────────────────────────┐
        │  身分服務（Supabase Auth）      │  帳號密碼、Google 登入、驗證信、重設密碼
        │  發出 access token（JWT）      │  公開金鑰：JWKS 網址
        └──────────────┬───────────────┘
                       │ 使用者登入後拿到 token
     ┌─────────────────┼──────────────────┐
     ▼                 ▼                  ▼
 adventure（Cloudflare） trilog（Vercel）     未來服務（任何位置）
 驗 token → 查本服務的   驗 token → 查本服務   驗 token → 查本服務
 授權名單／角色          的資料與權限          的授權
```

- 身分服務只回答「這個 token 是誰、email 是否已驗證」。
- 每個服務各自保存授權資料，例如 adventure 的 `EDITOR_EMAILS`、`VIEWER_EMAILS`（日後改成以使用者編號 `sub` 為鍵）。

## 四、Token 約定（所有服務共同遵守）

| 欄位 | 用途 |
|---|---|
| `sub` | 使用者唯一編號（UUID），**授權以它為準**，不以 email 為準 |
| `email`、`email_confirmed_at` | 只有 email 已驗證才可用於比對名單 |
| `aud` | 受眾：各服務只接受發給自己的 token（待確認 Supabase 的實際設定方式） |
| `exp` | 過期時間；過期由前端用 refresh token 換新，服務不接受過期 token |
| 角色（選用） | 第一版**不放進 token**，由各服務自己查；之後若需要集中管理，再評估 Supabase 的自訂 token 欄位功能（待查證） |

## 五、共用驗證模組（介面草案）

各服務各自實作同一個介面，行為一致：

- `verifyToken(token, { jwksUrl, audience })` → `{ sub, email, emailVerified }` 或拋出錯誤。驗簽章、`exp`、`aud`、簽發者。
- `authorize(app, user)` → `'editor' | 'viewer' | null`。第一版為各服務本地名單。
- 公開金鑰要快取並在 `kid` 對不上時重抓一次（adventure 目前驗 Cloudflare Access 的做法已是如此，可直接沿用）。

## 六、登入體驗（含 iOS 主畫面網頁）

1. 登入頁提供「用 Google 繼續」與「email 加密碼」。
2. **工作階段存放：優先用伺服器設定的 HttpOnly cookie，並設長有效期**；refresh token 在背景換新，使用者不會感覺到。比純瀏覽器 localStorage 耐用（iOS 對網站儲存有清除機制，主畫面網頁是否豁免待查證）。
3. 登入有效期（Supabase 的 session 時限與 refresh token 設定）待查證，目標是「一般使用幾週不用重登」。
4. 登入頁導向 Google 時，iOS 主畫面網頁可能跳到 Safari，回來時 cookie 是否保留待實測。

## 七、與現有系統的關係（重要限制）

- **trilog** 目前的 Supabase 專案同時是帳號與資料庫，資料表用 `auth.uid()` 做列層級權限（RLS）。若把 trilog 的帳號搬到另一個身分專案，**RLS 會失效，必須重寫**。因此 trilog 暫時維持現狀，不在第一階段搬動。若要讓資料庫接受外部身分來源的 token，需評估 Supabase 的第三方驗證功能（待查證）。
- **adventure** 目前用 Cloudflare Access（email 一次性驗證碼）。它沒有資料庫綁定，可先遷移。

## 八、階段

| 階段 | 內容 | 驗收 |
|---|---|---|
| 0（現在） | Cloudflare Access 加 Google 登入並拉長登入有效期，解決每次重登的不便 | 手機幾天不用重登 |
| 1 | 建立專屬身分專案（Supabase），設定 Google 與密碼登入、信件範本、登入有效期；寫共用驗證模組 | 用兩種方式都能登入並取得可驗證的 token |
| 2 | adventure 換成自己驗 token：登入頁、Worker 驗證、名單授權、手機登入維持；移除 Access | 四種身分（未登入、只讀、可編輯、不在名單）複查通過 |
| 3 | 新服務一開始就用共用模組 | — |
| 4（待決定） | trilog 是否遷移，或改接第三方驗證 | 另行評估 |

## 九、風險

1. 登入在 adventure 的 Worker 與靜態頁自己處理，安全責任增加；用現成函式庫、不自寫密碼處理。
2. 身分服務成為所有服務的單點：它出問題，所有服務都登不進去；需要備援與監控的想法。
3. 開放註冊後會有垃圾帳號與濫用：需要驗證信、頻率限制與（可能的）人機驗證。
4. 個資：身分專案只存必要資料；隱私條款需涵蓋共用登入。

## 十、待查證（官方文件，目前連不到）

- Supabase：非對稱簽章金鑰與 JWKS 公開網址、session 時限設定、自訂 token 欄位、第三方驗證（讓資料庫接受外部 token）、能否當 OIDC 提供者。
- Cloudflare Access：session 最長時限、Google 登入在目前方案是否可用。
- iOS：主畫面網頁的 cookie 與 localStorage 保存規則、Google 登入跳轉行為。
