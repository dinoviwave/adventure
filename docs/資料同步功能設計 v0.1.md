# 資料同步功能設計 v0.1

日期：2026-11-06（2026-11-07 補充實測結果）
範圍：「雙半馬冒險路線」頁面與 intervals.icu 之間的資料同步。此功能也是目標遊戲化方法中「外部資料來源」零件的第一個實作。

## 一、決定事項（Dino 已確認）

- 觸發方式：排程自動同步與手動同步並存
- 同步內容：課表（計畫）、完成的活動、賽事與階段備註、體能與恢復指標
- 衝突處理：以 intervals.icu 為準。課表的名稱、日期、類型與時長每次都覆蓋；頁面上勾選的完成狀態與標記的關鍵課表保留
- 課表名稱一律使用 intervals.icu 的原名，不改寫

## 二、基本限制

頁面無法連到外部網址，也不能保存金鑰，所以同步一定由頁面以外的角色執行：對話中的 Claude，或排程任務。頁面只負責顯示結果、顯示同步狀態、留下同步請求。同步是單向的：intervals.icu 到頁面。頁面不寫回 intervals.icu。

## 三、整體流程

1. 觸發：排程時間到，或 Dino 在對話中要求，或頁面上有待處理的同步請求
2. 讀取：只用 GET 讀取 intervals.icu 的 events、activities、wellness
3. 比對：與頁面資料庫現有文件比對，產生新增、更新、移除、略過的清單
4. 寫入：批次寫入頁面資料庫（一批最多 50 筆，已存在的文件需帶版本）
5. 記錄：寫一筆同步紀錄，頁面顯示「上次同步」時間與結果

可選的預覽模式：只產生差異清單，不寫入，由 Dino 確認後再寫。第一次同步與規則變更後建議使用。

## 四、資料對應規則

### 課表（WORKOUT events 到 workouts）

- 文件編號：`icu-{event id}`，同一課表永遠對應同一文件，可重複同步
- 欄位覆蓋：`title`（原名）、`date`、`kind`、`mins`
- 類型對應：Run 對應「跑」；Ride、VirtualRide、MountainBikeRide 對應「騎」；Swim 對應「游」；WeightTraining 對應「肌力」；其他對應「其他」
- 時長：事件的 `moving_time` 秒數換算成分鐘
- 保留頁面欄位：`done`、`doneAt`、`key`
- intervals.icu 已刪除的課表：頁面上尚未完成的就刪除；已完成的保留並標示「已從 intervals.icu 移除」
- 搬移日期：以新日期更新，文件編號不變

### 完成的活動（activities）

- 比對規則依序為：活動名稱包含課表名稱（例如「土城區 - 南山銳1_WED_跑步Z2」包含「南山銳1_WED_跑步Z2」）；同一天、同一運動類型且只有一筆候選
- 比對成功：該課表標記完成，記錄 `doneAt`（活動開始時間）、實際時長、距離、均心率、訓練負荷
- 比對不成功：建立計畫外文件 `icu-act-{activity id}`，標題用活動原名，備註放距離、時間、均心率、負荷；不計入準備度
- 略過：時長不到 2 分鐘或距離為 0 的活動（例如誤觸的 27 秒紀錄），列在同步報告的「略過」項目，不寫入
- 一個課表對到多筆活動時，取時長最接近計畫者，其餘列為計畫外

### 賽事與階段備註

- RACE_A、RACE_B、RACE_C 寫入 `races`：名稱、日期、優先級；頁面目前把賽事寫死在程式裡，之後改為讀這份資料
- NOTE（`external_id` 以 `phase-` 開頭）寫入 `phases`：名稱、起訖日、說明；結束日為最後一天的隔天，換算時要減一天。頁面用它取代目前寫死的週次標籤

### 體能與恢復指標（wellness）

- 寫入 `wellness`，文件編號為日期：CTL、ATL、TSB（CTL 減 ATL）、靜息心率、HRV、睡眠時數、睡眠分數
- 日期以起床當天為準，該日的睡眠是前一晚的睡眠
- 缺資料判定：睡眠時數為 0、或 HRV 為空值時標記 `missing`，靜息心率視為估算值；缺資料的日子不參與任何放行或準備度判斷
- 同步延遲：靜息心率可能先到，HRV 晚幾小時才補上。每次同步都重讀最近 3 天，補上延遲的資料

### 讀取範圍

- 課表與賽事：從階段起始日（目前 11/2）到最後一場賽事後一週
- 活動：從階段起始日到今天
- 體能指標：從階段起始日到今天，加上最近 3 天重讀

## 五、頁面資料庫新增項目

| 集合 | 用途 |
|---|---|
| `workouts`（既有） | 新增 `icuId`、`actual`（實際時長、距離、均心率、負荷）、`removedFromIcu`、`source` |
| `races` | 賽事清單，來自 RACE 事件 |
| `phases` | 階段備註 |
| `wellness` | 每日體能與恢復指標 |
| `syncLog` | 每次同步一筆：時間、觸發來源（排程、對話、頁面請求）、讀取範圍、新增、更新、移除、略過筆數、錯誤 |
| `syncRequests` | 頁面按鈕留下的請求：時間、狀態（待處理、已處理） |

## 六、頁面需要的改動

1. 同步狀態列：顯示「上次同步 11/6 22:05，新增 2，更新 1」。超過 24 小時沒同步時改成提醒顏色；最近一次同步失敗時顯示失敗原因
2. 同步按鈕：點下去只會留下一筆待處理請求，並顯示「已送出，等待處理」；它不會立刻同步，要等排程或對話處理。這點要在頁面上寫清楚，避免誤會
3. 課表列：顯示時長；已完成者顯示實際時長與距離；已從 intervals.icu 移除者標示
4. 頂部指標：新增體能一欄（CTL、ATL、TSB），缺資料時顯示「缺資料」而非數字
5. 地圖週節點：階段名稱改讀 `phases`；賽事改讀 `races`
6. 對不上的項目：同步報告中有未配對的課表或活動時，頁面提示數量，點開可看清單

## 七、排程

- 建議時間：每天 07:00 與 22:00。Dino 的訓練多在中午與 20:40 至 21:20 左右結束，22:00 能涵蓋晚間訓練；07:00 能補上前一晚的睡眠與 HRV
- 賽前一週可加密，但排程任務最短間隔通常為一小時，不需要更頻繁
- 排程任務每次是全新的對話，提示詞必須完整獨立（見附錄）
- 頁面請求只在排程時間才會處理；需要立即更新時，Dino 直接在對話中要求

## 八、金鑰與安全

- 已確認的限制：intervals.icu 的個人 API Key 只有一組，無法另外產生專用或唯讀的 Key。這組 Key 擁有帳號的寫入權限，重新產生後舊的立刻失效，Dino 其他使用 Key 的流程（例如貼上《Dino Intervals API》文件的新對話）也會一併失效，需要全部更新
- 因此同步程序必須在提示詞中明確限定：只能使用 GET，不得使用 POST、PUT、DELETE
- 實測（2026-11-07）：請求必須帶一般的 User-Agent（例如 `Mozilla/5.0 (compatible; viwave-sync)`），用 Python 預設的 User-Agent 會被回 403，改用後回 200
- 金鑰不得寫進頁面資料庫、頁面程式、專案文件或記憶
- 三種金鑰處理方式：
  1. 只在對話中手動同步：每次由 Dino 貼上 Key，不存放任何地方。最安全，但無法自動排程
  2. 把 Key 放進排程任務的提示詞：可自動同步，但能看到該任務設定的人都能看到 Key；之後每次重新產生 Key，都要同步更新排程
  3. 改用 OAuth：intervals.icu 論壇有 OAuth 支援的討論，若可行，排程只保存可撤銷、可限定範圍的權杖，不暴露個人 Key。但如何為個人使用的應用程式申請，尚未確認
- 目前對話中貼過的 Key，建議在決定處理方式後重新產生
- 第一版不做任何寫回 intervals.icu 的功能。之後若要做（例如由頁面建立課表），需另行討論並單獨確認

## 九、失敗與例外處理

| 情況 | 處理 |
|---|---|
| 401（金鑰無效或被重新產生） | 寫一筆失敗紀錄，頁面顯示「同步失敗：金鑰失效」；不修改任何資料 |
| 429（請求過多） | 等待後重試一次，仍失敗則記錄並結束 |
| 部分讀取失敗 | 只寫入成功讀取的部分，紀錄失敗項目；不刪除任何文件 |
| Garmin 尚未同步 | 剛練完讀不到活動屬正常，下次同步會補上，不算失敗 |
| 讀到的課表數量為 0 | 視為可疑，不執行刪除，只記錄警示 |
| 寫入版本衝突 | 重讀該文件後重新比對，再寫一次 |

## 十、驗收項目

1. 連續執行兩次同步，第二次應為 0 新增、0 更新（可重複執行）
2. 在頁面勾選完成並標記關鍵課表後再同步，兩者不被覆蓋
3. 在 intervals.icu 搬移一筆課表日期後同步，頁面上同一文件的日期改變
4. 刪除一筆未完成的課表後同步，頁面上對應文件被移除；刪除已完成者則保留並標示
5. 27 秒的誤觸活動被略過，並出現在報告中
6. 手錶沒電的日子，wellness 標記缺資料，不影響準備度
7. 故意使用錯誤的金鑰，頁面顯示同步失敗且資料不變
